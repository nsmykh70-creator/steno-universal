# PS23 — дорожная карта SLZ: скорость и сжатие

Состояние на начало PS23 (после PS22 + u64-ускорение, все числа — bench-s20
или CLI-замеры на этой машине, roundtrip = true везде):

| датасет | SLZ сейчас | xz | gzip | zstd -19 |
|---|---|---|---|---|
| fb2 (47.5 МБ) | 30.2% @ enc 17.2 / dec 160 | 16.8% @ 1.95 / 220 | 26.8% @ 11.7 / 139 | 26.7% @ 187 / 710 |
| m10 (10 МБ) | 53.2% @ enc 14.7 / 131 | 44.2% @ 3.1 / 93 | 50.2% @ 23.3 / 161 | 51.1% @ 201 / 595 |
| БД JSONL (10.5 МБ) | 11.8% @ enc ~26 / 263 | 7.5% @ 3.8 / 191 | 11.1% @ 63 / 250 | 11.5% @ 276 / 994 |

Уже сделано в PS22/PS22.1: окно 16 МиБ, lazy-1, MTF-офсеты, канонический
Хаффман по чанкам 1 МиБ + три таблицы последовательностей, u64-словесное
сравнение при расширении совпадений (enc fb2 ×1.6: 10.3 → 17.2 МиБ/с без
изменения размера).

## Сделано в PS23.1 (дополнительная итерация, 60/60 тестов)

1. **Word-copy декодер перекрывающихся повторов**: off==1 — fill одним
   байтом; off>8 — копирование 8-байтовыми шагами (первые off байт из
   исходных данных, хвост — из записанного участка). Декод RLE-данных:
   10 МиБ нулей — 0.026 с (**409 МиБ/с** против ~131 на побайтовом push).
2. **MAXMATCH 65535 → 1<<20**: раны до 1 МиБ — один токен (10 МиБ нулей
   сжимаются в 1518 Б одной последовательностью). Попутно расширена
   таблица частот длин (33 → 38 символов; размер передаётся в потоке,
   формат обратно совместим по структуре).
3. **«Редкие вставки» краёв**: для совпадений длиннее 32 в хеш-цепочки
   вставляются только первые/последние 16 позиций (раньше — каждая).
   enc fb2 ещё −10% (2.64 с, **17.9 МиБ/с** CLI), цена по размеру:
   fb2 +0.005%, db +0.19%, m10 +0.002%.

CLI-замеры после PS23.1: fb2 enc 17.9 / dec 165 МиБ/с; m10 enc 12.9 /
dec 131; db enc 25 / dec 268; roundtrip = true на всех трёх.

## Сделано в PS23.2 (эта итерация, 61/61 тестов)

1. **CRC32-хеш** (`crc32q`, sse4.2 через runtime-детекцию, fallback
   multiply-shift): enc fb2 −8% против PS23.1 на том же хосте (медиана
   3.02 → 2.77 с) и −0.003 п.п. размера (распределение кандидатов чуть
   точнее). Хост после пересборки песочницы медленнее прежнего —
   абсолютные числа разных итераций сравниваются только внутри одной
   машины.
2. **get_unchecked + read_unaligned** в горячем цикле расширения
   совпадений (границы доказаны инвариантами, debug_assert оставлен).
3. **Prefetch цепочки — замерен и отклонён**: +8–15% ко времени enc на
   fb2 в обоих вариантах (с prefetch input и без него) — данные почти
   всегда уже в кэше, а инструкции prefetch стоят тактов. Удалён.
4. **Живое сравнение с fast-классом**: bench-s20 получил строки lz4 и
   snappy (чистые Rust-порты lz4_flex/snap, в том же процессе) и явные
   уровни zstd -3 / zstd -19; cargo-тест `live_codec_comparison`
   печатает таблицу slz/lz4/snappy (slz 1.2% vs lz4 8.3% vs snappy
   11.3% на смешанных 960 КиБ — SLZ в 7–9 раз сильнее fast-класса).
   Зависимости Cargo.toml существуют только для сравнений и не влияют
   на формат.
5. **Исправлен мислейбл**: до PS23.2 строка «zstd» в bench-s20 звала
   дефолтный уровень 3 и в ранних отчётах помечалась как «zstd -19».
   Настоящий zstd -19: fb2 16.75% @ 1.29 МиБ/с (чуть лучше xz по
   размеру), db 7.41% @ 1.40. Таблицы PS22_BENCH_RU.md переписаны.

## Сделано в PS23.3 (эта итерация, 64/64 тестов)

1. **Уровни скорости slz-1…slz-19** — пресеты (глубина цепочки, lazy,
   GOOD_LEN): 1 = (8, 0, 16) greedy-без-lazy, 3 = (16, 8, 24), 6 = дефолт
   (32, 16, 48), 12 = (64, 24, 96), 19 = (128, 32, 256). CLI:
   `slz <in> <out> --level N`. **slz-1 — прямой конкурент lz4**:
   fb2 36.4% @ enc 50.8 / dec 144 МиБ/с против lz4 46.90% @ 226 (slz-1
   на 10.5 п.п. сильнее при 4.4× уступке в скорости); db 14.7% @ 75.7
   против lz4 18.98% @ 585 (в 7.7× медленнее, на 4.3 п.п. сильнее) —
   строка PS22-slz-1 добавлена в bench-s20.
2. **rep0-офсеты**: совпадение по «последнему офсету» mtf[0] кодируется
   одним селектором REP_SEL=29 без передачи офсета, MTF не сдвигается;
   сильный rep (≥8 Б) принимается сразу без обхода цепочек. Найден и
   исправлен при реализации конфликт экстра-бит (encode_chunk трактовал
   sel=29 как «новый офсет с 25 битами остатка»). Эффект на наших
   данных нейтрален (fb2 +0.0006%, db +0.002%, m10 −0.045% с учётом
   raw-escape) — механизм рассчитан на структурированные данные с
   равными интервалами (таблицы, записи).
3. **Raw-escape**: чанк, не ужавшийся ниже исходника, пишется целиком
   с флагом 1 — гарантия «не хуже хранения»; декодер копирует чанк
   memcpy-скоростью. MAGIC поднят до SLZ2 (формат менялся); на обеих
   сторонах MTF ресетится при raw-чанке, чтобы rep0/MTF-слоты
   оставались синхронны. На fb2/db/m10 escape не срабатывает (все чанки
   сжимаются), выигрыш проявится на случайных/зашифрованных данных.
4. Ошибка «магия не SLZ2» для пустого потока исправлена (минимальный
   валидный поток = 7 Б).

## Сделано в PS23.4 (эта итерация, 64/64 тестов) — шаг к cost-aware

1. **Стоимость-осознанное правило rep0**: rep берётся при равной длине
   с кандидатом (та же покрышка, минус символ) и при кандидате лишь
   незначительно длиннее — но только если кандидат ДАЛЁКИЙ (off > 64
   КиБ: экстра-бит офсета окупают потерю байтов). Первая версия правила
   (бонус для всех офсетов) фрагментировала длинные матчи fb2: enc
   18.5 → 12.5 МиБ/с — найдено замером и сужено; fb2 вернулся к 17.6.
2. **Фильтр дальних коротких совпадений**: кандидат с off > 1 МиБ
   принимается только при длине ≥5, off > 4 МиБ — ≥8 (короткий матч
   с дорогим офсетом дороже литералов). Порог 6 Б откатывался до 5
   после замера db (JSONL-ключи на дальних офсетах прибыльны и по 4-5 Б).
   Итог L6: m10 53.130 → 53.050% и enc 11.2 → 14.1 МиБ/с; db enc
   20.8 → 27.5 МиБ/с при +0.015 п.п.; fb2 30.180 → 30.177%.
3. **lazy2 для уровней 12/19**: lazy-проверка i+1 выполняется и при уже
   найденном совпадении (длинный матч может блокировать более длинный
   шагом дальше), пресеты 12 = (64, 32, 96), 19 = (128, 48, 256).
   Результат: **L12 fb2 28.38% / m10 52.81% / db 11.34%; L19 fb2
   27.12% @ 3.0 МиБ/с / m10 52.66% @ 6.7 / db 11.14% @ 7.8** — L19
   на 3.1 п.п. сильнее дефолта, размер уровня gzip при enc 4× медленнее
   gzip и dec 5× быстрее. Полный оптимальный парсер (суммарная стоимость
   пути по всем позициям) остаётся в PS24.

## Сделано в PS24.1 (эта итерация, 67/67 тестов) — словарный режим

1. **Формат SLZ3** (`slz --dict ФАЙЛ` / `slz-decode --dict ФАЙЛ`):
   `SLZ3` + uvarint(исходная длина) + uvarint(длина словаря) +
   uvarint(CRC-64 словаря) + чанки. Словарь в поток не пишется — обе
   стороны передают его отдельно; декодер проверяет длину и CRC-64.
   Магия SLZ2 не переиспользуется: декодер PS23.4 честно отвергает SLZ3
   («магия не SLZ2») — откат на старый релиз безопасен. Попутно
   исправлен `get_uvarint`: CRC-64 требует 10-байтовый varint (старый
   лимит 56 бит резал старший бит хеша).
2. **Раздельная dict-таблица кандидатов** (аналог dictMatchState у
   zstd): prime-проход пишет позиции словаря в `head_dict`, цепочки
   входа не загрязняются повторами словаря. Первая версия (общие
   цепочки) ухудшала сжатие на синтетике (19.2 против 16.9 КиБ) —
   найдено тестом и переделано. Prime идёт в обратном порядке: головой
   цепочки становится ранняя позиция словаря — вход, ссылающийся на
   словарь в порядке роста записей, находит полные совпадения сразу.
   Декод: офсет за пределами выхода читается из хвоста словаря; матч,
   пересекающий границу dict→out — прогрессирующая копия.
3. **Замер** (db_events.jsonl: тест — хвост 10 000 строк → 50 файлов
   по ~54 КиБ, словарь — голова 128 КиБ / 1 МиБ, зоны дизъюнктны;
   benchmarks/PS24_DICT_BENCH.csv): slz-6 16.00% → **13.66% со
   словарём 128 КиБ (−2.34 п.п.)**; словарь 128 КиБ оказался лучше
   1 МиБ (13.66 против 13.76) и в 8 раз дешевле по prime/CRC (enc 1.7
   против 1.4 МиБ/с, dec 20.4 против 10.4). slz-19+dict — 12.99%.
   Контекст: zstd-3+dict(110 КиБ обученный) — 12.45%, zstd-19+dict —
   9.02%, gzip — 12.74%, zstd-1 — 13.77%. Вывод: механизм работает и
   даёт выигрыш на малых файлах, SLZ остаётся позади zstd на 1.2 п.п.
   на этом профиле (Хаффман вместо FSE, короткие словарные цепочки) —
   закрывается FSE и cost-aware парсером (PS24). Накладной расход:
   prime+CRC словаря на каждый файл (~3 мс при 128 КиБ).

## Мероприятия по убыванию «выгода / усилия»

### 1. Raw-escape для несжимаемых чанков — ✅ сделано в PS23.3 (см. выше)
Если закодированный чанк ≥ исходного — писать чанк как есть с флагом.
Сейчас несжимаемые участки бинарных данных могут «распухать» (частично
видно на m10: 53.2% против gzip 50.2%). Гарантирует «никогда не хуже
хранения» и убирает провалы на случайных/зашифрованных данных. Декод —
чтение флага, нулевая цена для сжимаемых чанков.

### 2. Уровни скорости slz-1…slz-19 — ✅ сделано в PS23.3 (см. выше)
Константы уже изолированы: DEPTH, LAZY_DEPTH, GOOD_LEN, BLOCK, окно.
Замер на fb2 (это ядро будущей шкалы):

| DEPTH | размер fb2 | enc |
|---|---|---|
| 32 (сейчас) | 30.18% | 10.3 → 17.2 МиБ/с (после u64) |
| 48 | 29.29% | 6.9 МиБ/с |
| 64 | 28.65% | 5.6 МиБ/с |

DEPTH 32→64 даёт −1.53 п.п. размера за ×1.8 времени — классическая
шкала уровней без единой строки нового алгоритма. Верхние уровни —
плюс lazy-2 и двухшаговый выбор кандидатов.

### 3. Rep0-смещение — ✅ сделано в PS23.3 + стоимость-правило в PS23.4 (см. выше)
Как у zstd: последний офсет (rep0) проверяется всегда, даже если хеш не
дал кандидата, и кодируется одним символом. На БД-данных и структурированных
записях поля повторяются на близких дистанциях — ожидаемо −1…−3 п.п. на
JSONL/CSV, на тексте −0.5 п.п.

### 4. FSE/ANS вместо Хаффмана для последовательностей (усилия: дни)
Хаффман тратит ≥1 бит/символ; FSE дробит бит. У zstd это главный источник
преимущества над deflate. Ожидаемо −1…−2 п.п. на всех данных, декод не
медленнее (таблицы конечного состояния читаются за 1 lookup). Держать
Хаффман как дешёвый режим «level ≤ N».

### 5. Cost-aware парсер (усилия: 1–2 недели, главный резерв сжатия)
Жадный+lazy выбор «самого длинного» совпадения заменяем оценкой цены в
битах: цена литерала = −log2 p из реальной Хаффман-таблицы чанка, цена
совпадения = биты селектора офсета + биты длины + цена литерального рана.
Локальный ДП на окно ~4 КиБ, как zstd btopt/btultra. Ожидаемо −2…−5 п.п.
на тексте (главный разрыв с gzip именно в парсере: у deflate-9 жадность
уже «стоимостная»), −1…−3 п.п. на бинарных и БД. Скорость enc падает в
1.5–3 раза только на верхних уровнях.

### 6. Многопоточный encode (усилия: дни)
Чанки Хаффмана независимы; окно 16 МиБ общее. Два пути: (а) конвейер —
токенизация чанка k+1 параллельно с кодированием чанка k (накладные
расходы ~0); (б) полная независимость блоков со сбросом окна, как
multithread-zstd (цена ~0.5–1 п.п.). На 8 ядрах — enc ×6…×7. Декод
остаётся однопоточным (как у zstd).

### 7. Словарный режим для мелких записей БД — ✅ база сделана в PS24.1 (см. выше)
`--dict` работает (SLZ3, раздельная dict-таблица, CRC-64). На 50 файлах
db по ~54 КиБ: 16.00% → 13.66% (−2.34 п.п. при словаре 128 КиБ).
Дальше по этому пункту: тренированный словарь (выборка частотных
фрагментов вместо сырой головы, как zstd --train), переиспользование
Tok между файлами в одном процессе (prime один раз), запись словаря
рядом с пачкой файлов. Для коротких строк (1–4 КиБ) ожидание ×2…×5
сохраняется.

### 8. Колоночная упаковка БД (усилия: отдельный проект, большой резерв)
JSONL разбирается по ключам на колонки (ts, user_id, event, …), каждая
сжимается отдельно: энумераторы — почти в ноль (таблица значений),
timestamp — дельта+varint, числа — битовая упаковка, остаток текста — SLZ.
Так работают BtrBlocks/Capstone в современных СУБД; на нашем db_events
ожидаемо 11.8% → 2–4% (порядка steno-пайплайна 5.6%, а по колонкам —
лучше), при скорости, близкой к SLZ.

### 9. Мелочи
- prev[] 64 МиБ ужимать до размера файла (округление вверх до степени 2) —
  CLI на маленьких файлах ест меньше памяти; скорость не меняется.
- 2-уровневая таблица декода Хаффмана (2^10 + 2^4) — быстрее сборка
  таблиц (3 на чанк) и меньше кэш-давление; запас по dec ~10–20%.
- Хеш-бакеты на 2 слота и хеш 5–6 байт для бинарных данных — точнее
  кандидаты на m10 (−0.5…−1.5 п.п. при том же DEPTH).
- Хвост «добиваемых» литералов после последнего совпадения чанка кодировать
  отдельным раном в заголовке чанка — убирает редкий граничный перерасход.

### 10. Дешёвая «тройка» для enc без изменения формата (идеи PS23.2)
- **CRC32-инструкция для хеша** (`crc32q`): быстрее и равномернее
  multiply-shift; enc +3–8%.
- **Prefetch следующего узла цепочки** (`_mm_prefetch` адреса
  `prev[cand]`): prev[] на 64 МиБ — главный cache-killer больших окон;
  enc +5–15%.
- **get_unchecked в горячих циклах** (границы доказаны инвариантами,
  debug-сборка остаётся с проверками): enc +5–15%.

### 11. Декод: двойные символы и переиспользование таблиц
- **Двухсимвольный декод литералов** (таблица пар, 2 символа за lookup):
  dec +20–30% на литерал-тяжёлых данных (fb2 — 82% байтов это литералы).
- **Флаг «таблица не изменилась»** между соседними чанками: экономит
  ~300 Б/чанк и пересборку трёх таблиц 2^15 на чанк; на малых файлах
  dec +3–7%.
- **Entropy prescan чанка**: байт-гистограмма; энтропия > 7.95 бит/Б —
  raw-escape сразу (enc на случайных данных ×10 быстрее, в паре с п.1).

### 12. Форматные идеи среднего масштаба
- **Статический словарь Brotli-стиля** (~13 КиБ частых русских/JSON
  фрагментов + transform'ы префиксов/суффиксов): fb2/db −1…−2 п.п.
  бесплатно для dec.
- **Дельта-офсеты между записями БД**: у последовательных JSONL-записей
  расстояния до прошлых повторов почти равны; кодировать разность
  офсетов соседних записей — db −1…−2 п.п.
- **Адаптивный размер чанка**: несжимаемый чанк → следующий вдвое
  мельче (быстрее адаптация таблиц на гетерогенных данных, как m10).
- **SIMD-скан литеральных ранов** (LZ4-стиль, 16-байтовые сравнения
  при поиске длины несовпадения).

## Ожидаемый итог к PS24

Уровни: slz-1 ≈ 55+ МиБ/с (raw-escape, DEPTH 8–16), slz-9 ≈ 15–20 МиБ/с
(сейчас это PS22.1), slz-19 ≈ 4–6 МиБ/с с cost-aware+FSE — fb2 ~24–26%,
БД ~8–9%, «никогда не хуже gzip на наших данных, всегда ≥3× быстрее xz
по сжатию». Дальше — только колоночный режим для БД и CM-слой «slz-hi»
(order-1 арифметика на литералах, −3…−5 п.п. ценой dec ×2–3) — сфера,
где уже царит полный steno-пайплайн.
