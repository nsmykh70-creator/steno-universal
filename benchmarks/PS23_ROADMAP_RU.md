# PS23 — дорожная карта SLZ: скорость и сжатие

Состояние на начало PS23 (после PS22 + u64-ускорение, все числа — bench-s20
или CLI-замеры на этой машине, roundtrip = true везде):

| датасет | SLZ сейчас | xz | gzip | zstd -19 |
|---|---|---|---|---|
| fb2 (47.5 МБ) | 30.2% @ enc 17.2 / dec 160 | 16.8% @ 1.95 / 220 | 26.8% @ 11.7 / 139 | 26.7% @ 187 / 710 |
| m10 (10 МБ) | 53.2% @ enc 14.7 / 131 | 44.2% @ 3.1 / 93 | 50.2% @ 23.3 / 161 | 51.1% @ 201 / 595 |
| БД JSONL (10.5 МБ) | 11.8% @ enc ~26 / 263 | 7.5% @ 3.8 / 191 | 11.1% @ 63 / 250 | 11.5% @ 276 / 994 |

Уже сделано в PS22/PS22.1: окно 16 МиБ, lazy-1, MTF-офсеты, канонический
Хаффман по чанкам 1 МиБ + три таблицы последовательностей, u64-словесное
сравнение при расширении совпадений (enc fb2 ×1.6: 10.3 → 17.2 МиБ/с без
изменения размера).

## Сделано в PS23.1 (дополнительная итерация, 60/60 тестов)

1. **Word-copy декодер перекрывающихся повторов**: off==1 — fill одним
   байтом; off>8 — копирование 8-байтовыми шагами (первые off байт из
   исходных данных, хвост — из записанного участка). Декод RLE-данных:
   10 МиБ нулей — 0.026 с (**409 МиБ/с** против ~131 на побайтовом push).
2. **MAXMATCH 65535 → 1<<20**: раны до 1 МиБ — один токен (10 МиБ нулей
   сжимаются в 1518 Б одной последовательностью). Попутно расширена
   таблица частот длин (33 → 38 символов; размер передаётся в потоке,
   формат обратно совместим по структуре).
3. **«Редкие вставки» краёв**: для совпадений длиннее 32 в хеш-цепочки
   вставляются только первые/последние 16 позиций (раньше — каждая).
   enc fb2 ещё −10% (2.64 с, **17.9 МиБ/с** CLI), цена по размеру:
   fb2 +0.005%, db +0.19%, m10 +0.002%.

CLI-замеры после PS23.1: fb2 enc 17.9 / dec 165 МиБ/с; m10 enc 12.9 /
dec 131; db enc 25 / dec 268; roundtrip = true на всех трёх.

## Мероприятия по убыванию «выгода / усилия»

### 1. Raw-escape для несжимаемых чанков (усилия: часы, риск: нулевой)
Если закодированный чанк ≥ исходного — писать чанк как есть с флагом.
Сейчас несжимаемые участки бинарных данных могут «распухать» (частично
видно на m10: 53.2% против gzip 50.2%). Гарантирует «никогда не хуже
хранения» и убирает провалы на случайных/зашифрованных данных. Декод —
чтение флага, нулевая цена для сжимаемых чанков.

### 2. Уровни скорости slz-1…slz-19 (усилия: часы)
Константы уже изолированы: DEPTH, LAZY_DEPTH, GOOD_LEN, BLOCK, окно.
Замер на fb2 (это ядро будущей шкалы):

| DEPTH | размер fb2 | enc |
|---|---|---|
| 32 (сейчас) | 30.18% | 10.3 → 17.2 МиБ/с (после u64) |
| 48 | 29.29% | 6.9 МиБ/с |
| 64 | 28.65% | 5.6 МиБ/с |

DEPTH 32→64 даёт −1.53 п.п. размера за ×1.8 времени — классическая
шкала уровней без единой строки нового алгоритма. Верхние уровни —
плюс lazy-2 и двухшаговый выбор кандидатов.

### 3. Rep0-смещение (усилия: часы–день)
Как у zstd: последний офсет (rep0) проверяется всегда, даже если хеш не
дал кандидата, и кодируется одним символом. На БД-данных и структурированных
записях поля повторяются на близких дистанциях — ожидаемо −1…−3 п.п. на
JSONL/CSV, на тексте −0.5 п.п.

### 4. FSE/ANS вместо Хаффмана для последовательностей (усилия: дни)
Хаффман тратит ≥1 бит/символ; FSE дробит бит. У zstd это главный источник
преимущества над deflate. Ожидаемо −1…−2 п.п. на всех данных, декод не
медленнее (таблицы конечного состояния читаются за 1 lookup). Держать
Хаффман как дешёвый режим «level ≤ N».

### 5. Cost-aware парсер (усилия: 1–2 недели, главный резерв сжатия)
Жадный+lazy выбор «самого длинного» совпадения заменяем оценкой цены в
битах: цена литерала = −log2 p из реальной Хаффман-таблицы чанка, цена
совпадения = биты селектора офсета + биты длины + цена литерального рана.
Локальный ДП на окно ~4 КиБ, как zstd btopt/btultra. Ожидаемо −2…−5 п.п.
на тексте (главный разрыв с gzip именно в парсере: у deflate-9 жадность
уже «стоимостная»), −1…−3 п.п. на бинарных и БД. Скорость enc падает в
1.5–3 раза только на верхних уровнях.

### 6. Многопоточный encode (усилия: дни)
Чанки Хаффмана независимы; окно 16 МиБ общее. Два пути: (а) конвейер —
токенизация чанка k+1 параллельно с кодированием чанка k (накладные
расходы ~0); (б) полная независимость блоков со сбросом окна, как
multithread-zstd (цена ~0.5–1 п.п.). На 8 ядрах — enc ×6…×7. Декод
остаётся однопоточным (как у zstd).

### 7. Словарный режим для мелких записей БД (усилия: дни)
Тренируем словарь (8–112 КиБ) на выборке, пишем его в контейнер/рядом,
каждая запись сжимается как continuation словарного окна. Для коротких
строк (1–4 КиБ) это ×2…×5 к сжатию — сегодня короткая запись почти не
сжимается, потому что ей не с чем совпадать. Идеальная пара к колоночному
режиму.

### 8. Колоночная упаковка БД (усилия: отдельный проект, большой резерв)
JSONL разбирается по ключам на колонки (ts, user_id, event, …), каждая
сжимается отдельно: энумераторы — почти в ноль (таблица значений),
timestamp — дельта+varint, числа — битовая упаковка, остаток текста — SLZ.
Так работают BtrBlocks/Capstone в современных СУБД; на нашем db_events
ожидаемо 11.8% → 2–4% (порядка steno-пайплайна 5.6%, а по колонкам —
лучше), при скорости, близкой к SLZ.

### 9. Мелочи
- prev[] 64 МиБ ужимать до размера файла (округление вверх до степени 2) —
  CLI на маленьких файлах ест меньше памяти; скорость не меняется.
- 2-уровневая таблица декода Хаффмана (2^10 + 2^4) — быстрее сборка
  таблиц (3 на чанк) и меньше кэш-давление; запас по dec ~10–20%.
- Хеш-бакеты на 2 слота и хеш 5–6 байт для бинарных данных — точнее
  кандидаты на m10 (−0.5…−1.5 п.п. при том же DEPTH).
- Хвост «добиваемых» литералов после последнего совпадения чанка кодировать
  отдельным раном в заголовке чанка — убирает редкий граничный перерасход.

### 10. Дешёвая «тройка» для enc без изменения формата (идеи PS23.2)
- **CRC32-инструкция для хеша** (`crc32q`): быстрее и равномернее
  multiply-shift; enc +3–8%.
- **Prefetch следующего узла цепочки** (`_mm_prefetch` адреса
  `prev[cand]`): prev[] на 64 МиБ — главный cache-killer больших окон;
  enc +5–15%.
- **get_unchecked в горячих циклах** (границы доказаны инвариантами,
  debug-сборка остаётся с проверками): enc +5–15%.

### 11. Декод: двойные символы и переиспользование таблиц
- **Двухсимвольный декод литералов** (таблица пар, 2 символа за lookup):
  dec +20–30% на литерал-тяжёлых данных (fb2 — 82% байтов это литералы).
- **Флаг «таблица не изменилась»** между соседними чанками: экономит
  ~300 Б/чанк и пересборку трёх таблиц 2^15 на чанк; на малых файлах
  dec +3–7%.
- **Entropy prescan чанка**: байт-гистограмма; энтропия > 7.95 бит/Б —
  raw-escape сразу (enc на случайных данных ×10 быстрее, в паре с п.1).

### 12. Форматные идеи среднего масштаба
- **Статический словарь Brotli-стиля** (~13 КиБ частых русских/JSON
  фрагментов + transform'ы префиксов/суффиксов): fb2/db −1…−2 п.п.
  бесплатно для dec.
- **Дельта-офсеты между записями БД**: у последовательных JSONL-записей
  расстояния до прошлых повторов почти равны; кодировать разность
  офсетов соседних записей — db −1…−2 п.п.
- **Адаптивный размер чанка**: несжимаемый чанк → следующий вдвое
  мельче (быстрее адаптация таблиц на гетерогенных данных, как m10).
- **SIMD-скан литеральных ранов** (LZ4-стиль, 16-байтовые сравнения
  при поиске длины несовпадения).

## Ожидаемый итог к PS24

Уровни: slz-1 ≈ 55+ МиБ/с (raw-escape, DEPTH 8–16), slz-9 ≈ 15–20 МиБ/с
(сейчас это PS22.1), slz-19 ≈ 4–6 МиБ/с с cost-aware+FSE — fb2 ~24–26%,
БД ~8–9%, «никогда не хуже gzip на наших данных, всегда ≥3× быстрее xz
по сжатию». Дальше — только колоночный режим для БД и CM-слой «slz-hi»
(order-1 арифметика на литералах, −3…−5 п.п. ценой dec ×2–3) — сфера,
где уже царит полный steno-пайплайн.
